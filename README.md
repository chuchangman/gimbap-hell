# 🍣 김밥지옥 — 웨이브 디펜스 (3D · 1인칭 · 멀티플레이)

손님이 **웨이브로 밀려옵니다.** 다 같이 쌀을 씻고 밥을 짓고 속재료를 손질해
**주문에 맞는** 김밥을 말아, 인내심이 다하기 전에 내보내세요.

손님은 두 종류입니다. **일반 손님은 키오스크로만 주문**해서 가게에 나타나지 않고
화면 오른쪽 주문 목록에만 뜹니다. **진상 손님은 카운터에 직접 와서** 커스텀 조합을
요구하고, 인내심이 훨씬 빨리 닳으며 말풍선으로 궁시렁댑니다.
인내심이 0이 되면 손님은 그냥 돌아가고 **점수와 평판이 깎입니다.**
평판이 바닥나면 폐업, **10웨이브**를 넘기면 완주입니다.

그리고 주방에는 **빗자루가 3개** 있습니다. 협동만 하리라는 보장은 없습니다.

---

## 실행

```bash
npm install     # socket.io 하나만 받습니다 (three.js 는 동봉되어 있습니다)
npm start
```

터미널에 **팀원에게 보낼 주소가 그대로 출력**됩니다.

```
  ➜ http://localhost:3211
  📡 팀원에게: http://70.12.247.229:3211   (같은 Wi-Fi)
```

한 명이 **가게 이름을 정하고 새 가게 열기** → 나머지는 **방 코드 4글자**로 입장 → 방장이 **영업 시작**.
가게 이름은 끝나고 **랭킹에 올라갑니다.**
비워두면 방장 닉네임을 따서 **「홍길동의 가게」** 가 됩니다.
**최대 6명**, 2~5명을 권합니다. 설치할 것은 없고 브라우저만 있으면 됩니다.

팀원이 못 들어오면 거의 항상 방화벽입니다. 방장 PC 에서 관리자 PowerShell 로 한 번만:

```powershell
netsh advfirewall firewall add rule name="Gimbap 3211" dir=in action=allow protocol=TCP localport=3211
```

### 자동 검증

```bash
npm test
```

브라우저 없이 서버 로직만 돌려 **108개 항목**을 검사합니다.
재료 8종 공정 · 설비 개수 · 키오스크/진상 손님 구분 · 웨이브별 재료 해금 ·
주문 자동 최적 매칭 · 빗자루 사거리/쿨다운/넉백 · 평판 0 폐업 · 10웨이브 완주 ·
가게 이름 정리와 점수 순 랭킹까지 확인합니다.
(랭킹 테스트는 임시 파일에 쓰므로 실제 기록을 건드리지 않습니다)

**충돌 처리가 있습니다.** 조리대·냉장고·칸막이·벽은 물론 **동료도 통과할 수 없습니다.**
좁은 주방에서 길을 막는 것부터가 이미 훼방입니다.

## 웨이브 디펜스

```
준비 25초 → 웨이브 1 → 준비 18초 → 웨이브 2 → ... → 웨이브 10 → 완주
                                   ↑ 평판 0 이 되면 그 자리에서 폐업
```

손님은 모두 문으로 들어와 **카운터에 줄을 섭니다.** 주문은 전부 **김밥 1줄**입니다.

| | 👤 일반 손님 | 🧔 진상 손님 |
|---|---|---|
| 주문 | **기본 3종 + 해금된 재료를 얹은 것** | **커스텀 조합 3~5종** (기본 3종 규칙 예외) |
| 인내심 | 기준값 | **×0.62 — 훨씬 빨리 닳음** |
| 반응 | — | 인내심 구간마다 말풍선으로 궁시렁 |
| 놓쳤을 때 | 점수 −60 · 평판 −12 | 점수 −60 · **평판 −18** |
| 비중 | 80% | **20%** |

**손님을 조준하고 E** 를 누르면 그 손님에게 바로 나갑니다.
조준이 귀찮으면 🛎️ 서빙 창구에 내도 되는데, 그때는 **조합이 가장 잘 맞는 주문**으로 자동 배정됩니다.
어느 쪽이든 완전히 맞으면 만점, 재료가 빠지거나 쓸데없이 더 들어가면 그만큼 깎입니다.
화면에 `일치 87%` 처럼 미리 보여줍니다.

화면 **왼쪽 위 주문서**에 손님별로 필요한 재료가 **이름으로** 뜨고,
조립대에 넣은 재료는 **줄이 그어집니다.** 조준 중인 손님은 금색으로 강조됩니다.

### 10개 웨이브 (3인 기준)

주문은 전부 1줄이므로 **손님 수 = 만들어야 할 김밥 줄 수**입니다.

| 웨이브 | 손님 | 인내심 | 등장 간격 | 해금 |
|---|---|---|---|---|
| 1 | 2명 | 110초 | 20초 | — |
| 2 | 3명 | 105초 | 18초 | 🦀 맛살 |
| 3 | 5명 | 100초 | 14초 | 🥒 오이 |
| 4 | 6명 | 95초 | 11초 | 🥚 계란 |
| 5 | 7명 | 90초 | 11초 | — |
| 6 | 9명 | 84초 | 8초 | 🥕 당근 |
| 7 | 10명 | 78초 | 8초 | — |
| 8 | 12명 | 72초 | 8초 | 🍢 어묵 |
| 9 | 14명 | 66초 | 7초 | — |
| 10 | 16명 | 58초 | 6초 | — |

카운터 자리는 **6개**입니다. 넘치는 손님은 밖에서 기다리다 자리가 나면 들어옵니다.

**난이도는 두 축으로 올라갑니다** — 주문 수·주문량이 늘고, 인내심이 줄어듭니다.
거기에 **재료가 하나씩 해금**되면서 주문 조합이 점점 복잡해집니다.

**인원수에 맞춰 손님 수가 자동 조정됩니다.** 표는 3인 기준이고,
1인이면 약 0.53배, 5인이면 약 1.47배가 됩니다 (`scaleCount`).

**속도는 김밥 제작 시간에 맞췄습니다.** 한 줄에 혼자면 20~30초, 분업하면 10~15초 걸립니다.
설비를 늘린 만큼(화구5·도마3·조립대3·밥솥2) 처리량이 올라갔지만 재료가 8종으로 늘어
손이 더 가므로, 등장 간격을 그보다 넉넉히 잡았습니다.

## 김밥 만드는 법

### 1. 밥 짓기

```
🧊 냉장고에서 쌀 → 🚰 싱크대에서 5번 헹굼 (E 연타) → 🍚 밥솥 10초 취사 → 밥 5인분
```

한 번 취사하면 **김밥 5줄 분량**이 나옵니다.
**준비 시간에 밥부터 안치는 것**이 이 게임의 기본기입니다.

밥솥이 **2대**라 한 대를 돌리는 동안 다른 한 대를 채울 수 있습니다.

### 2. 속재료 8종

| 재료 | 공정 | 장소 | 시간 | 해금 |
|---|---|---|---|---|
| 🟡 단무지 | 썰기 | 도마 | 3초 | 처음부터 |
| 🥓 햄 | 볶기 | 가스렌지 **팬** | 5초 | 처음부터 |
| 🥬 시금치 | 데치기 | 가스렌지 **냄비** | 5초 | 처음부터 |
| 🦀 맛살 | **손질 불필요** | — | — | 웨이브 2 |
| 🥒 오이 | 썰기 | 도마 | 3초 | 웨이브 3 |
| 🥚 계란 | 지단 부치기 | 가스렌지 **팬** | 6초 | 웨이브 4 |
| 🥕 당근 | 볶기 | 가스렌지 **팬** | 4초 | 웨이브 6 |
| 🍢 어묵 | 볶기 | 가스렌지 **팬** | 5초 | 웨이브 8 |

목표 시간에 가까울수록 품질 100. 너무 오래 두면 못 쓰게 되어 음쓰통행입니다.
가스렌지는 **냄비 2 + 프라이팬 3** 으로, 팬을 쓰는 재료가 4종이라 팬을 더 뒀습니다.

해금 안 된 재료는 냉장고에 🔒 로 잠겨 보이고, 해금되는 웨이브가 안내됩니다.

### 3. 말고 썰어서 서빙

```
🍙 조립대 ×3: 김 → 밥 → 속재료 → 말기 3초
🔪 도마 ×3:   김밥 썰기 3초
🛎️ 서빙 창구: 조합이 맞는 주문으로 자동으로!
```

순서가 강제됩니다. 김 없이 밥부터 올릴 수 없고, 밥 없이 속재료를 넣을 수 없습니다.
빈손으로 조립대에 E 를 누르면 맨 위 재료를 되돌립니다.

같은 재료를 두 번 넣을 수는 없습니다.

### 재료를 더 넣고 싶다면

`public/js/config.js` 의 `ITEMS` 에 항목을 추가하고
`FRIDGE_ROW_A/B` · `EXTRA_FILLINGS` · `UNLOCKS` 에 id 를 넣으면 그대로 게임에 들어옵니다.

## 🧹 빗자루 난투

가게에 빗자루가 **3개** 놓여 있습니다. **E** 로 집고 **Q** 로 제자리에 돌려놓습니다.

- **좌클릭으로 휘두릅니다.** 우상 → 좌하 대각선으로 내려칩니다
- **동료뿐 아니라 손님도** 때릴 수 있습니다 (아래 참고)
- 사거리 **2.6m**, 정면 **±70도**, 쿨다운 **0.65초**
- 맞은 사람은 **포물선을 그리며 날아가고 들고 있던 걸 놓칩니다**
- 단, **빗자루를 들면 재료를 못 듭니다.** 훼방에는 대가가 따릅니다

거리·각도·쿨다운은 **서버가 다시 검사**하므로 클라이언트를 고쳐도 뚫리지 않습니다.
빗자루를 든 채 나가면 자동으로 제자리에 돌아옵니다.

## 🎯 누구에게 줄지 고르기

김밥을 **잘라서 손에 들면** 화면 **우측**에 그 김밥의 속재료가 이름으로 펼쳐집니다.

동시에 그 김밥과 **가장 잘 맞는 주문**의 손님에게 **보라색 윤곽선**이 생깁니다.

- 똑같이 맞는 손님이 여럿이면 **전부** 표시됩니다 (아무에게나 줘도 같은 점수).
  그중 **실제로 나갈 한 명**만 밝게 숨쉬고 나머지는 흐리게 깔립니다
- 윤곽선은 **내 클라이언트에서만** 그려집니다 — 동료 화면에는 안 보입니다
- three.js 애드온 없이 **역방향 헐**(몸통·머리를 살짝 키워 `BackSide` 로 그리기)로 만듭니다
- 테두리는 늘 몸통 *바깥* 이라 배경 위에 얹힙니다. 손님 뒤는 크림색 벽뿐이라
  **어두운 보라**를 씁니다 — 밝은 하늘색은 대비 1.17:1 로 조리 거리에서 안 보였습니다
- 거리에 따라 배율을 보정해 화면에서 **약 4px 두께**를 유지합니다

좌측 주문서의 **줄 긋기**는 그중 **가장 급한 한 명**에게만 갑니다.

| 손 상태 | 비교 기준 | 줄이 그어지는 사람 |
|---|---|---|
| 김밥을 들었을 때 | 그 김밥의 속재료 | 가장 잘 맞는 손님 중 가장 급한 한 명 |
| 만드는 중 | 조립대에 넣은 재료 | 〃 |
| 아무것도 안 넣었을 때 | (비교 불가) | 그냥 가장 급한 손님 |

이 규칙은 `config.js` 의 순수 함수 `focusPick()` 하나가 계산하고,
서버의 `waves.bestMatch()` / `nextTarget()` 과 **같은 규칙**입니다.
그래서 화면에 표시된 손님과 **실제로 서빙되는 손님이 어긋나지 않습니다** (테스트로 교차 검증).

## 🌊 웨이브가 끝나면

손님을 다 치우면 화면 **중앙 상단**에 크게 뜹니다.

```
        ✅ 웨이브 3 클리어
   😊 만족 5 · 😡 놓침 1 · 곧 웨이브 4
```

- 토스트는 우르르 쌓여 놓치기 쉬워서, 웨이브 종료만 따로 크게 알립니다
- 숫자는 **그 웨이브 몫**입니다 — 누적이 아닙니다
- 마지막 웨이브를 넘기면 금색 **🎉 완주!** 로 바뀝니다

**클리어 자체에는 점수를 주지 않습니다.** 점수는 손님을 만족시켜야만 나옵니다 —
웨이브를 버티기만 해서는 오르지 않습니다.

## 😤 손님 쫓아내기

손님마다 머리 위에 **체력바**가 있습니다. 빗자루로 때려 **0** 으로 만들면 쫓겨납니다.

| | 체력 | 비고 |
|---|---|---|
| 키오스크 일반 손님 | **3대** | |
| 카운터 진상 손님 | **5대** | 맷집이 좋습니다 |

- 한 대에 **1칸**씩 깎이고, 맞은 손님은 **움찔거리며 붉게** 물듭니다
- 0 이 되면 **문 밖으로 걸어 나갑니다** ("여기 두 번 다시 안 와")
- 대가: **점수 -25 · 평판 -6**

평판 손해가 시간 초과(**일반 -12 / 진상 -18**)보다 **적게** 잡혀 있습니다.
재료가 아직 안 풀렸거나 도저히 못 맞출 커스텀 주문이 걸렸을 때
**손절하고 다음 손님으로 넘어가는** 선택지입니다.

빗자루를 든 채 손님을 조준하면 남은 체력이 화면 아래 안내에 뜨고,
좌측 상단 주문서에도 하트(♥)로 표시됩니다.
사거리·정면 판정은 **서버가 다시 검사**합니다.

## 🏆 가게 랭킹

영업이 끝나면 **가게 이름 · 점수 · 도달 웨이브**가 랭킹에 기록되고,
결과 화면에서 **역대 몇 위인지** 와 **상위 10개 가게**를 보여줍니다.
10위 밖이면 목록 아래에 이번 판을 따로 붙여줍니다.
**대기실 좌측**에도 상위 10개가 뜹니다 (좁은 화면에선 본문 아래로 내려갑니다).

- 랭킹에 나오는 가게 이름은 **첫 글자만 보이고 나머지는 `●` 로 가립니다**
  (`동네김밥집` → `동●●●●`). 가리는 건 **서버**가 합니다 —
  클라이언트에서만 가리면 `GET /leaderboard.json` 에 원본이 그대로 나오기 때문입니다.
  대기실 상단에 크게 뜨는 **내 가게 이름은 안 가립니다**
- 가게 이름을 안 정하면 **「방장닉의 가게」** 로 자동 설정됩니다 (16자 제한)
- 정렬: **점수 내림차순** → 도달 웨이브 → 먼저 세운 기록 우선
- 저장 위치: `data/leaderboard.json` (서버를 껐다 켜도 남습니다, 최대 200건)
- `GET /leaderboard.json` 으로 상위 50개를 그냥 받아볼 수도 있습니다
- 저장 경로는 `GIMBAP_LEADERBOARD` 환경변수로 바꿀 수 있습니다
- 저장되는 값은 **원본 그대로**입니다. 가리는 건 내보낼 때만 (`publicTop` / `publicBoard`)

### 닉네임

**2~12글자**입니다. 클라이언트가 먼저 걸러주지만 최종 판정은 서버가 합니다
(`room.mjs` 의 `nameError`) — 소켓으로 직접 쏴도 막힙니다.

기록을 지우고 싶으면 `data/leaderboard.json` 을 지우면 됩니다.

## 점수

| 상황 | 점수 |
|---|---|
| 김밥 한 줄 서빙 | +10 × (품질/100) |
| 손님 주문 완료 | +(60 + 남은 인내심 비율 × 40) × (품질/100) |
| 진상 손님 주문 완료 | 위 점수 **×1.5** |
| 일반 손님이 그냥 나감 | **−60 · 평판 −12** |
| 진상 손님이 그냥 나감 | **−60 · 평판 −18** |
| 재료를 바닥에 버림 (Q) | −5 (음쓰통은 감점 없음) |

**김밥 품질 = 속재료의 평균 조리 품질 × 주문 맞춤도.**
맞춤도는 주문에서 빠진 재료마다 −0.28, 쓸데없이 더 넣은 재료마다 −0.14 입니다.
불 조절을 아무리 잘해도 **주문과 다르면 점수가 안 나옵니다.**

## 공정 해석 메모

원본 요구사항의 **"쌀 → 밥 밥솥 10초 5번"** 은 이렇게 나눴습니다.

- **5번** → 싱크대에서 쌀을 **5번 헹굽니다** (`TIME.riceRinse`)
- **10초** → 밥솥 취사 시간 (`TIME.riceCook`)
- 한 솥에서 **밥 5인분** (`TIME.riceYield`) — 취사를 걸어두고 속재료를 손질하는 흐름이 생깁니다

다르게 읽으셨다면 `config.js` 의 `TIME` 세 값만 바꾸면 됩니다.

## 배포 (Render)

이 저장소에는 `render.yaml` Blueprint 가 들어 있어 Render 가 설정을 자동으로 읽습니다.

| 항목 | 값 |
|---|---|
| 빌드 | `npm ci` |
| 실행 | `npm start` (= `node server/index.mjs`) |
| 헬스체크 | `/health` -> `{"ok":true,"rooms":n,"store":"file|redis","entries":n}` |
| 포트 | `process.env.PORT` (Render 가 주입) |
| 리전 | `singapore` (한국에서 가장 가까운 무료 리전) |

[render.com/blueprints](https://dashboard.render.com/blueprints) 에서 이 저장소를 고르면
끝입니다. `main` 에 푸시하면 자동으로 재배포됩니다 (`autoDeploy: true`).

### 랭킹 저장소 — 무료 플랜에선 Upstash 가 필요합니다

Render 무료 플랜은 **파일 시스템이 휘발성**입니다. 재배포할 때뿐 아니라
**15분 미사용으로 잠들었다 깨어나기만 해도** `data/leaderboard.json` 이 통째로
사라집니다. 경로를 바꿔도 같은 휘발성 디스크 안이라 소용이 없습니다.

그래서 `leaderboard.mjs` 는 저장 위치를 두 가지로 둡니다.

| 환경변수 | 저장 위치 |
|---|---|
| 없음 | `data/leaderboard.json` (로컬 개발 · 자체 호스팅) |
| `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN` | Upstash Redis |

무료 Upstash 붙이는 법:

1. [console.upstash.com](https://console.upstash.com) 에서 GitHub 로그인 -> **Create Database**
2. Type `Redis`, Region 은 `ap-northeast-1` (도쿄) 정도로
3. 만든 DB 의 **REST API** 패널에서 `UPSTASH_REDIS_REST_URL` 과
   `UPSTASH_REDIS_REST_TOKEN` 두 값을 복사
4. Render 서비스 -> **Environment** 에 그대로 붙여넣고 저장 (자동 재배포됨)

키 이름은 기본이 `gimbap:leaderboard` 이고, `GIMBAP_LEADERBOARD_KEY` 로 바꿀 수 있습니다.
무료 티어가 하루 1만 명령인데 이 게임은 **판이 끝날 때 쓰기 1회**뿐이라 남아돕니다.

동작 방식은 이렇습니다. 읽기(`top`/`size`/`board`)와 쓰기(`add`)는 전부 **동기**로
남겨뒀습니다 — `room.mjs` 가 `add()` 바로 다음 줄에서 `board()` 를 부르기 때문입니다.
메모리 캐시가 사실상의 원본이고, Upstash 쓰기는 뒤에서 비동기로 따라갑니다.
그래서 **Upstash 가 죽어도 게임은 그대로 돌아가고**, 그 판 기록만 남지 않습니다.
어느 저장소를 쓰는지는 `/health` 로 밖에서 바로 확인할 수 있습니다.

    curl https://<서비스>.onrender.com/health
    {"ok":true,"rooms":0,"store":"redis","entries":12}

`store` 가 `file` 이면 환경변수가 안 들어간 것이고, `storeError` 가 붙어 있으면
URL 이나 토큰이 틀린 것입니다. 부팅 배너에도 같은 내용이 찍힙니다.

### 그 밖에 무료 플랜에서 알아둘 것

- **15분 미사용 시 잠듭니다.** 다시 깨어나는 데 ~50초 걸리니, 사람들을 모아
  테스트하기 전에 미리 한 번 열어서 깨워두는 편이 좋습니다.
- Socket.IO 실시간 통신(WebSocket)은 무료 플랜에서도 그대로 동작합니다.
- 인스턴스가 하나라서 메모리 캐시가 갈릴 일이 없습니다. 유료로 올려
  인스턴스를 여러 개 굴릴 거라면 랭킹 쓰기를 Redis 원자 연산으로 바꿔야 합니다.
